# G-PID 架构优化方案 / Architecture Refactor Proposal

> 编制 2026-09-06（W3 收尾）· 基线 Godot-PID-Core 46 脚本 / 6,811 行 · Godot 4.7
> 依据：《Godot-PID 24 周开发运营计划 C 版》《架构审查 2026-09-05》《架构评审 2026-09-04》
> Copyright © 2026 Jonson Wang

**EN Abstract.** This proposal maps the 20-week feature backlog (W4–W24 of the C-version
roadmap) onto the current codebase, identifies five structural gaps, and proposes a
five-layer target architecture: a new **`app/` application-service layer** inserted between
UI and kernel, decomposition of the three god-objects (1,640 / 1,084 / 1,087 lines) into 17
single-responsibility files, a **canvas Tool pattern** for interaction extensibility, and
**8 extension seams** (command stack, connect service, validator, exporter, document
manager, off-page link, graph traversal, AI rule engine) so that every future weekly feature
lands as a *new file* rather than a modification of core.

---

## 1. 现状：分层是对的，问题在界面堆积与服务层缺失

依赖方向严格向下、无循环依赖，这是重构可以大胆进行的基础。已有四件做对的事必须保住：

| 已做对 | 说明 |
|---|---|
| 依赖单向 | `core` 从不引用 `ui`/`render`/`autoload` |
| 视图是数据的纯投影 | `GPGraphBinder` 增量同步；`GPSymbolView` 重绑 def 即实现「改模板→全实例刷新」 |
| 纯模块先行的抽离习惯 | `GPCanvasCamera` / `GPCanvasSelection` / `GPGeometry` / `GPPopupHelper` 都是成功先例 |
| JSON 自管序列化 | 不走 `.tres`，单文件 `*.pid.json` 可 Git diff，数据主权成立 |

**代码分布**：三大巨型文件 3,811 行 = 全部代码 56%。

| 文件 | 行数 | 成员函数 | 状态 |
|---|---:|---:|---|

## 2. 五个结构性缺口（W4–W24 功能映射）

| 周次 | 要求能力 | 现状 | 缺失抽象 |
|---|---|---|---|
| W4 | 端口吸附 + 连接合法性 | 端口几何基础具备，**无吸附无校验** | `GPConnectService` |
| W5 | 属性面板 + UndoRedo + 实例缩放 | **无 UndoRedo**；`GPPIDNode` 无 `gpScale` | `GPCommand` / `GPCommandStack` |
| W6 | 存档 + 跨图同步 + promote + 影响范围提示 | `GPProjectIO` 可用但**调用内联在 main_window 89 行** | `GPProjectService` |
| W10/W18 | 属性 schema 校验 + 合规校验器 | `gpAttrsSchema` 已存但**从未被读** | `GPValidator` / Registry |
| W11 | BOM 清单导出 | `list_basic.gd` 12 行桩，**无统一接口** | `GPExporter` + Registry |
| W20 | 2D-3D 联动（需图形态遍历） | **图算法为零**；`PID3DBuilder` 返回空 Node3D | `GPGraphTraversal` |
| W21/W22 | 多 P&ID / 跨图纸互连 | `GPPIDGraph` 是**单图纸**；`AppState` 是桩 | `GPDocumentManager` / off-page |
| W23 | AI 规则引擎 | 仅 `UnitOperationDef` 数据桩，**text→片段通路不存在** | `GPUnitOperationRule` |
| W9 | 复制粘贴/对齐/分布/分组 | 框选已有，但**剪贴板与对齐全无**且深埋画布 | `GPClipboard` / `GPAlignService` |
| W15 | 上千图元性能 | `clip_contents` 已开；但 `_draw()` 逐帧全量遍历 | 脏标记 + 视口裁剪 + 空间索引 |

**「改不动」的三个具体症状**

1. **状态爆炸**：`GPCanvas2D` 顶部 269 行全是成员变量，60+ 个（`_gpDrawFrom`/`_gpPolyPts`/`_gpGripDrag`/`_gpMarqueeing`/`_gpShapeDragIdx`/`_gpPanning`…）。每加一个交互工具再塞 5–8 个。
2. **无法单测**：交互逻辑与 `Control` 生命周期绑死。W16「测试守护核心」目前一行 UI 逻辑都测不了。
3. **重复已三次**：`_gpAuthorPorts` 与 `GPSymbolNormalizer._gpDenormalizePorts` 逐字相同；`._gpHitShape` 是 `GPGeometry.gpShapeHit` 的弱化版（忽略曲线/弧）；`._gpTranslateShape` 与 `GPGeometry.gpShiftPoints` 重复。

## 3. 目标架构：五层

```
L5 ui/      界面（薄）：只做事件翻译与渲染，不含业务规则
              shell/ canvas/ tools/ panels/ dialogs/
   ↓ 硬规则：ui 不得直接改图数据，一切变更经 app/ 的 Command 或服务
L4 app/     ★新增 应用服务层（用例编排 · 无 UI · 可 headless 测）
              GPCommandStack GPConnectService GPProjectService GPDocumentManager
              GPValidatorRegistry GPAlignService GPGraphTraversal GPRuleEngine
              GPClipboard GPSymbolEditCoordinator GPSymbolDeleteService GPSymbolSaver
   ↓
L0-L2 core/ + render/   内核（纯 · 严禁引用 ui/app/autoload）
              core/model/ core/geometry/ core/symbol/ core/service/ core/platform/
              render/
L- io/       ★导出升级为注册表模式：GPExporter 接口 + GPExportRegistry + dxf/pdf/csv/print
L- addons/ + autoload/   GPIPIDAddon 契约；I18n / Settings / AppState（业务逻辑下沉到 app/）
```

**为什么是「加一层 app/」而不是「继续塞进 core/」**
`core/` 是领域模型与算法——它不该知道「用户点右键该发生什么」；`ui/` 是渲染与事件——它不该知道
「删一个图元要级联哪些实例」。现在这两件事挤在同一个文件里（`main_window._gpCascadeDeleteSymbol`），
既不能单测也不能复用。`app/` 承担**用例编排**：调 core 的纯算法、驱动内核 API、发信号通知 UI 刷新；
它是纯 `RefCounted`，可 headless 完整测试——正好解掉 W16 的死结。

## 5. 核心设计：画布工具模式（Tool Pattern）

每加一种交互 = 新增一个文件 + 注册表加一行，画布主体**一行不改**。

```
_gui_input(event)                     ← GPCanvas2D 唯一入口，只做坐标换算与分派
      ↓
GPCanvasInteractState                 ← 共享状态：模式 · 选择集 · 相机 · 待放置图元
      ↓
GPCanvasToolRegistry                  ← 模式 int → 工具实例（字典）
      ↓
GPSelectTool | GPConnectTool★W4 | GPDrawShapeTool | GPPlaceTool | GPGripTool | GPAlignTool★W9
      ↓
一切变更封装为 GPCommand → GPCommandStack(W5) → 内核 API → gpGraphChanged → Binder 增量刷新
```

```gdscript
# ui/tools/canvas_tool.gd — 画布工具基类 / Canvas tool base class
class_name GPCanvasTool
extends RefCounted

# Shared context injected by the canvas. / 由画布注入的共享上下文。
var gpCtx: GPCanvasToolContext

# Called when the tool becomes / stops being the active one. / 工具激活 / 停用时调用。
func gpOnActivate() -> void: pass
func gpOnDeactivate() -> void: pass

# Input hooks. Return true when consumed (canvas will accept_event()).
# 输入钩子。返回 true 表示事件已被消费。
func gpOnPress(gpWorld: Vector2, gpShift: bool, gpDouble: bool) -> bool: return false
func gpOnMove(gpWorld: Vector2) -> bool: return false
func gpOnRelease(gpWorld: Vector2) -> bool: return false
func gpOnKey(gpKey: InputEventKey) -> bool: return false

# Overlay painting (rubber band, grips, preview). / 覆盖层绘制。
func gpDrawOverlay(gpCv: CanvasItem) -> void: pass
func gpCursor() -> int: return Input.CURSOR_ARROW
```

**这个设计直接买到的三件事**
- W4 连线：新增 `connect_tool.gd` + `connect_service.gd`，画布主体 0 行改动。
- W5 撤销：工具只提交 Command，撤销栈有了唯一收口。
- 可测性：工具是 `RefCounted`，headless 里构造假 Context 直接喂事件断言结果。

## 6. 可复用服务层（5 个立即可落地的新类）

| 新类 | 位置 | 职责与接口 | 解决什么 |
|---|---|---|---|
| **GPIOResult** | core/service | `{gpOk, gpCode, gpMessageKey, gpDetail}`；`gpOk()` / `gpFail(gpCode, gpKey)` | 「失败无原因」：promote/导出/校验失败都要把原因经 i18n 展示 |
| **GPIdGen** | core/service | `gpNext(gpPrefix)` / `gpEnsureUnique(gpId, gpTaken)` / `gpSanitize(gpName)` | 当前 `gpNextId` 是画布成员、"n%d"，`_gpUniqueId` 是对话框私有；W21/W22 要求**全局唯一 ID** |
| **GPCommand**<br>**GPCommandStack** | app | Command：`gpDo(gpCtx)`/`gpUndo(gpCtx)`/`gpLabel()`；Stack：`gpPush`/`gpUndo`/`gpRedo`/`gpClear`，信号 `gpStackChanged` | W5 UndoRedo。先自建薄栈（更可控可测），后续再考虑接 Godot UndoRedo |
| **GPConnectService** | app | `gpFindSnapPort(gpGraph, gpDefs, gpWorld, gpTol) -> Dictionary`；`gpCanConnect(gpGraph, gpFrom, gpTo) -> GPIOResult` | W4。规则集中一处，画布/右键菜单/AI 生成共用 |
| **GPProjectService** | app | `gpSave`/`gpOpen`/`gpAutosaveTick`/`gpIsDirty`；信号 `gpProjectLoaded/gpProjectSaved/gpDirtyChanged` | W6 存档 + W14 自动保存 .bak + 最近文件 |

## 7. 八个扩展接缝（seam）

定义好这 8 个接口后，W4–W24 每个新功能只需**新增实现文件**，核心与界面均不修改——
这正是 Open-Core 双仓所需：商业版 Pro 通过实现接口扩展，核心仓零改动。

```gdscript
# ── Seam 1 · 命令栈（W5） ────────────────────────────────────
class_name GPCommand extends RefCounted
func gpDo(gpCtx: GPCanvasToolContext) -> void: pass
func gpUndo(gpCtx: GPCanvasToolContext) -> void: pass
func gpLabel() -> String: return ""          # i18n key / i18n 键

# ── Seam 2 · 连接服务（W4） ──────────────────────────────────
class_name GPConnectService extends RefCounted
func gpFindSnapPort(gpGraph: GPPIDGraph, gpDefs: Array[GPSymbolDef],
        gpWorld: Vector2, gpTol: float) -> Dictionary
func gpCanConnect(gpGraph: GPPIDGraph, gpFromRef: String, gpToRef: String) -> GPIOResult

# ── Seam 3 · 校验器（W10 属性 / W18 合规） ────────────────────
class_name GPValidator extends RefCounted
func gpId() -> String                        # "isa5_1" / "iso10628" / "iec62424"
func gpValidate(gpGraph: GPPIDGraph, gpDefs: Array[GPSymbolDef]) -> Array[GPIssue]
# GPIssue = {gpSeverity, gpMessageKey, gpNodeId, gpField} —— 全部走 i18n key
# GPValidatorRegistry.gpRegister(v) / gpRunAll(g, d) -> Array[GPIssue]

# ── Seam 4 · 导出器（W11 清单 / DXF / PDF / 打印） ────────────
class_name GPExporter extends RefCounted
func gpId() -> String
func gpDisplayName() -> String               # i18n key
func gpExtension() -> String                 # "csv"
func gpExport(gpGraph: GPPIDGraph, gpDefs: Array[GPSymbolDef], gpPath: String) -> GPIOResult
# GPExportRegistry.gpRegister(e) / gpAll() / gpRun(id, g, d, path)

# ── Seam 5 · 文档管理器（W21 多 P&ID） ───────────────────────
class_name GPDocumentManager extends RefCounted
signal gpDocChanged(gpDocId: String)
func gpNewDoc(gpTitle: String) -> String
func gpActiveGraph() -> GPPIDGraph
func gpAllGraphs() -> Array[GPPIDGraph]
# 注：GPPIDGraph 本身就是「一张图纸」，管理器只持有 Array[GPPIDGraph] + 当前索引，
#    不新造 Document 类型 —— 把已有的东西用对即可。

# ── Seam 6 · 跨图互连（W22 off-page） ───────────────────────
# GPPIDEdge 扩展两个可选字段（全部 .get(key, default) 读取，向后兼容旧存档）：
#   gpKind    = "off_page"                        → 边代表跨图纸连接
#   gpCrossRef = {"doc": "D2", "tag": "P-101"}    → 对侧图纸与位号

# ── Seam 7 · 图算法（W20 2D-3D 联动） ───────────────────────
class_name GPGraphTraversal extends RefCounted
static func gpShortestPath(gpGraph: GPPIDGraph, gpFrom: String, gpTo: String) -> Array[String]
static func gpTraceLine(gpGraph: GPPIDGraph, gpFrom: String) -> Array[String]

# ── Seam 8 · AI 规则引擎（W23 单元操作生成） ──────────────────
class_name GPUnitOperationRule extends RefCounted
func gpMatch(gpText: String) -> bool                     # "离心泵+电机+入口过滤器"
func gpInstantiate(gpAnchor: Vector2) -> GPGraphFragment
# GPGraphFragment = {gpNodes: Array[GPPIDNode], gpEdges: Array[GPPIDEdge]}
# 关键：片段经 Command 一次性提交 → 天然可撤销、可复核、零幻觉。
```

> **⚠ Seam 5 的设计取舍：不要新造 Document 类型。** C 版指南提到 `GPPIDDocumentManager`，
> 直觉是新建 `GPDocument` 包装类。但 `GPPIDGraph` 本身就是完整图纸（meta / nodes / edges /
> shapes / 内嵌符号包 / 序列化），再加一层只会多一次转换和一个失步风险。
> 建议 DocumentManager 直接持有 `Array[GPPIDGraph]` + 当前索引 + 每图显示名/脏标记；
> `ui/center_area.gd` 已有的 `gpAddTab/gpActiveGraph/gpAllCanvases` 正是这套 API 的 UI 侧实现，
> 只需从「管理画布控件」升级为「管理图 + 画布」。

## 8. 迁移路线（与周计划对齐）

## 9. 架构护栏（建议写入 CONTRIBUTING.md）

1. **文件规模上限**：单文件 ≤ 400 行（硬上限 500）；单类成员函数 ≤ 20 个。`tools/` 脚本统计并告警。
2. **依赖方向单向**：core 严禁引用 app/ui/render/autoload；app 严禁引用 ui。`tools/check_architecture.gd` 自动扫描。
3. **UI 不得直改数据**：一切图数据变更经 Command 或服务。审查时 UI 脚本出现 `gpGraph.gpAdd*` 一律退回。
4. **新纯类必须带测试**：新增 core/ 或 app/ 下的纯类，同 PR 必须附 headless 测试（沿用 `GPGTest` 基类）。
5. **第二次出现即抽离**：同一逻辑第二次出现立即抽为共享类，不复制粘贴（参照 GPGeometry / GPPopupHelper 先例）。
6. **命名规范不妥协**：类 GP+Pascal、函数/变量 gp+camel、私有 _gp+、常量 GP_+；显式类型；双语注释；函数显式返回类型。

## 11. ⚠ 执行时必须注意的 Godot specifics（本项目已踩过的坑）

1. **移动文件必须同步 `.uid`**：Godot 4 资源 UID 与路径绑定，只 git mv 脚本会丢失引用。
   建议用编辑器内「移动到…」，或移动后重新导入。
2. **headless checker 的 preload 限制**：引用 I18n/Settings 的脚本不能在 checker 里 preload，
   必须在 `_initialize()` 里运行期 `load()`。新增 app/ 服务若引用 autoload，测试写法须遵此约束。
3. **`match` 缩进与信号形参**：搬迁时最易因缩进错位导致 `Could not parse global class` 连锁报错；
   信号回调形参数量必须 ≥ 信号实参数量（现有代码已踩过 2 次）。
4. **拆分类时的代理属性过渡**：先抽类、原文件保留同名 getter/setter 代理，确认零回归后再清理代理——
   这是 `GPCanvasCamera` / `GPCanvasSelection` 已验证的零回归路径。
5. **headless 校验：autoload 依赖脚本必须用场景运行，不能用 `--script`**：`--script`（`extends SceneTree` + `_initialize`）**不引导**项目 autoload（I18n/Settings/GPAppState），凡脚本在编译期直接引用这些全局单例会 `Compile Error: Identifier not found`；但 `godot --headless <scene>.tscn`（`extends Node` + `_ready`）会完整初始化 autoload。校验 harness 在 `_ready()` 期间 `get_tree().root` 正忙，向其 `add_child` 会失败，应把被测节点挂到 harness 自身下（`add_child(target)`）。P2 交互回归即按此模式（见 §14）。
