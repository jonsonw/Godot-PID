# Godot-PID 代码库架构审查报告（2026-09-05）

> 本报告为**纯架构评估**，未修改任何源码。数据基于 `Godot --headless --editor --quit`（EXIT=0 编译干净）+ 全仓 grep/wc 实测。
> 范围：`src/` 全部 59 个 `.gd`，总计约 8536 行。

## 一、总体判断

经过数轮重构（P0 统一图元模型 → P1/P2 抽共享几何/抓取点/popup → P3 抽工程 IO → 取消图元编辑器 → 生成图元对话框），**核心活动链路已经相当干净**：

- `core/` 纯数据层：`GPShape`/`GPPort`（Resource）、`GPGeometry`、`GPShapeGripEditor`、`GPShapeSpec`/`GPPortSpec` —— headless 可测、无 UI 依赖，是良好的"单一事实来源"。
- 视图同步 `graph_binder`/渲染 `symbol_view`/`edge_view`/`symbol_painter` 职责清晰。
- 存档 `project_io`、模型 `pid_graph`、图元库 `symbol_library` 边界清楚。

**但代码库同时存在三类"负债"**，按危害排序：

1. **大量孤立/桩模块（死代码集群）** —— 与已删除的 `symbol_edit_session` 同族的一批"愿望式设计"文件既不被 `main_window` 也不被任何 `.tscn` 实例化，形成自引用闭环，却增加了认知负担与误读风险。
2. **巨型文件 `canvas_2d.gd`（1614 行，61 个函数）** —— 相机 + 绘制 + 输入路由 + 选择 + 抓取点 + 右键菜单 + 连线预览 + 节点/图元操作全揉在一个类。
3. **`main_window.gd`（997 行）作为"上帝合成根"** —— 虽已抽出 `project_io`，仍承担菜单/工具栏/两栏 dock/对话框编排/图元库刷新等过多职责。

> 与 2026-09-04 版评审相比，**已解决**：双份抓取点/几何实现（P1 抽 `GPGeometry`+`GPShapeGripEditor`）、三套图元格式（P0 统一 `GPShape`/`GPPort`）、popup 定位重复（P2 抽 `GPPopupHelper`）、`main_window` 内联 IO（P3 抽 `GPProjectIO`）、图元编辑器冗余（已整套删除）。**本报告聚焦剩余负债**，不再重复已闭环项。

### 🟠 P1-1　`canvas_2d.gd`（1614 行 / 61 函数）职责过载

**问题**：单个类混入 6 大关注点——①相机/平移/缩放/坐标变换；②全部绘制（网格、注释图形、图元视图、抓取点、手柄）；③输入路由（`_gui_input` 分发到 绘制/选择/连线/节点/图元/抓取点/双击）；④选择模型（节点 `gpSelection` + 图形 `gpShapeSel` 两套）；⑤右键菜单声明+弹出+分发；⑥连线预览。

**后果**：改动一处常牵连他处；61 个函数使单文件难读；`_gpOnLeftDown`/`_gpOnKey` 等巨型 `match` 已有数处踩坑记录。

**建议（分层，非一次到位）**：
1. **`GPCanvasCamera`**：平移/缩放/`world↔screen` 变换（此前评审 P1 因符号编辑器无相机而未抽；现主画布是唯一有相机的，但抽出仍降低 `canvas_2d` 复杂度且使未来 3D/多视图可复用）。
2. **`GPCanvasModel`（选择集）**：封装"节点选择 `Array[String]` + 图形选择 `Array[int]`"的增删/框选/清空，替代散落的 `gpSelection`/`gpShapeSel` 操作。
3. **`_gpShowContextMenu` 的菜单声明表**：把 `id→文案→禁用条件→分发回调` 声明化为数据，缩小编排体积。
4. 目标：`canvas_2d` 降到 **< 700 行**（不含被抽走的相机/选择/菜单）。

**风险**：`canvas_2d` 是输入密集型、改错立即影响主流程。必须小步抽离、每步 `--editor --quit` 编译 + 交互目视验证。

### 🟡 P2-1　`symbol_normalizer.gd`（349 行）的 dict 交接面脆弱

**问题**：归一化器在 `gpDef.gpShapes`(强类型) 与 spec dict `{paths,circles,rects,box}` 之间反复转换，且刚补了 `_gpTransformShapes` 的 `handles` 透传（否则丢曲线）。这种 **"强类型 ↔ 裸 dict" 双轨**是多次踩坑源（`Array[X]` 类型错、`match case` 缩进、`var x: Dictionary = {...}` 解析、handles 丢失都发生在这一层）。

**建议**：逐步用 `GPShapeSpec.gpBuild/gpFromSpec` 收敛转换，让 `gpDef.gpShapeSpec()` 成为**唯一** dict 出口、`gpFromSpec` 成为唯一 dict 进口；normalizer 内部尽量操作 `GPShape` 而非裸 dict。为所有"往返无损"增加 headless 单测（尤其 handles/arc）。

### 🟢 P3　代码规范与边界约束固化

**建议写入 CONTRIBUTING / 评审清单**：
1. **core 纯净**：`core/` 只依赖 core + Resource，无 `Control`/`Window`/`Node` 依赖，可 headless 测。
2. **单向依赖**：`ui → render → core`；`core` 绝不反向依赖 `ui`。已核查 `canvas_2d` 无 `main_window` 反依赖（好），固化此约束。
3. **GDScript 硬坑黑名单**（已踩、写入注释/评审）：`@export` 数组须 `Resource`；`Array[X]` 形参须配 `Array[X]` 或放宽成 `Array`；`match case` 缩进须整段正确；`PopupMenu` 无 `popup_at_cursor`（用 `GPPopupHelper`）；多行 typed dict 字面量 `var x: Dictionary = {...}` 慎用；信号带参 → 槽回调须带默认值参数。
4. **单文件上限**：UI 类目标 **< 800 行**，超限即提示拆分。
5. **新模块须进主流程或明确归档**：禁止再产生"只被自己引用"的 `.gd`；加桩即标注 `# ARCHIVE/蓝图` 并在对应 `.tscn`/`main_window` 留 TODO 锚点，否则不提交。

## 三、目标分层与接口设计（建议蓝图）

```
┌─ ui/（Control/Window，输入编排，只发信号/调用）─────────────┐
│  main_window(合成根,瘦)  canvas_2d(画布+交互,瘦)            │
│  make_symbol_dialog  inspector  palette/grid/search          │
├─ render/（只读绘制，接受 core 模型/规格 dict）──────────────┤
│  symbol_painter  symbol_view  edge_view                     │
├─ core/（纯数据+纯逻辑，无 UI 依赖，headless 可测）──────────┤
│  shape/port/pid_graph/symbol_library/symbol_categories      │
│  geometry/shape_spec/shape_grip_editor/symbol_normalizer    │
│  project_io(单一持久化出口)                                  │
├─ model/（跨层共享的 Resource 数据类，可被 ui/core 引用）─────┤
│  symbol_pack(frame_def 若启用再立)                           │
└─ autoload/（i18n/settings/app_state）───────────────────────┘
```

**关键接口不变式**：
- `core` 暴露 `gpToDict/gpFromDict/gpBuild/gpFromSpec/gpShapeSpec` 为**唯一序列化契约**，dict 仅作 JSON/存档/渲染传输，不在 core 内部当工作类型。
- 新增形状类型 = 只改 `GPShape` + `GPGeometry` + `shape_spec`（一处多态，消除"改 3 处"旧模式）。
- 对话框/面板通过 `signal` 向 `main_window` 上报结果，`main_window` 只编排，不持有领域计算。

## 五、需防范的重构风险

1. **两套持久化并存误接线**（最高危）：若有人把 `GPPersistence`/backend seam 当成"应实现的正式接口"去重构掉可用的 `GPProjectIO`，会导致存档丢失/迁移断裂。→ 先归档/标注 seam，确保 `GPProjectIO` 是唯一被引用的存档出口。
2. **`canvas_2d` 输入路由拆分破坏交互**：拆相机/选择时，`world↔screen` 换算与命中容差耦合深，一次误换算即"菜单飞远/抓取点拖不动"类回归。→ 每次只抽一个关注点并 F5 目视四象限拖拽。
3. **删除死代码误伤 live 依赖**：`symbol_pack.gd`/`frame_def`(若未来启用)/渲染层是 LIVE，删除前必须 grep 排除。`.uid` 与 `.gd` 需成对处理。
4. **normalizer 往返无损被破坏**：handles/arc 若在某一转换面再丢，会重现"样条生成图元变直"问题。→ 固化 handles/arc 往返为必测项。
5. **i18n rename 漏点**：`symed.tool_*` 改 `canvas.tool_*` 若漏改 `main_window` 的 `I18n.gpTr` 调用 → 按钮显示裸 key。→ rename 后用 grep 对照 key 定义与引用一一对应。
6. **孤儿 `.uid` 未来 uid 冲突**：Godot 4 靠 uid 定位脚本；删除源文件不删 uid，新建同名脚本可能复用冲突 uid。

## 六、结论

代码库的**活的主干已相当健康**（core 纯逻辑层、渲染层、单一存档 `project_io`、`GPMakeSymbolDialog` 流程都已收敛，compile 零错误）。剩余问题集中在 **"外围愿望式死代码 + 巨型活动类 + 测试缺失"** 三类。

建议先做一轮 **"清场"（死代码归档 + uid 清理 + i18n 键域固化 + headless 测试基线）**，为后续 `canvas_2d`/`main_window` 的渐进拆分建立安全网；避免在无测试基线前对输入密集型类做大范围重排。分层与边界约定见第三节，可作为后续 CODE REVIEW 与新人开发的对照标准，防止滑向"屎山"。
