# ADR-6：导入默认非破坏

> 本 ADR 规定「导入图元包 / 工程片段」默认不覆盖既有内容；任何 id / uid / tag 冲突都由导入方派生新值。

## Status / 状态

Accepted（代码引用见 `io/project_import.gd:11`）

## Context / 背景

P&ID 是工程交付物。现场已经确认的位号（tag）、已经分配好的实例 uid、用户手写的图元 id，一旦被一次「导入」静默覆盖，就可能抹掉已签字的设计意图——这种丢失比「导入失败」严重得多。朴素导入会直接用导入来源的 id 覆盖本地同名实体，极易误伤。

需要一条铁律：导入永远是非破坏式的（non-destructive），冲突时让导入方让步。

## Decision / 决策

1. **绝不覆盖既有内容**：导入遇到 id / uid / tag 冲突，一律为导入方派生新值（重映射 uid、重编号 tag、必要时重命名 id），绝不回写本地已有实体；
2. **导入方让步，本地优先**：本地已存在的定义 / 图元优先保留，导入物以「新副本」身份并入；
3. **迁移链「已用 uid」集合不预填**：导入场景下的迁移链只服务于「导入物内部的旧→新 uid 重映射」，不可把「导入方已用过的 uid」预先填进目标的「已用集合」，否则会错误占用本地后续编号水位线；
4. **可覆盖为显式选项**：若用户明确选择「覆盖」，须作为独立确认动作，而非默认行为。

## Consequences / 后果

- 正向：用户数据主权得到制度性保护；一次手滑的导入不会抹掉现场确认的设计；导入可逆（删除导入副本即可）。
- 负向：导入后可能出现「两个长得一样但 uid 不同」的实体，需要 UI 给出清晰的合并/替换入口；
- 负向：导入逻辑比「直接覆盖」复杂，须维护 id 重映射表与 uid 分配器，且迁移链要区分「导入态」与「打开态」。
