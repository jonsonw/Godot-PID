# ADR-8：原生存档保持 JSON，DEXPI 只作交换方言

> 本 ADR 规定 `*.pid.json` 是唯一原生存档格式；DEXPI XML 只承担交换职责（导出目标 / 导入来源），不参与原生持久化。
> 触发问题：既然最终要产出 DEXPI XML，为何不直接把存档格式换成 XML，省掉转换？

## Status / 状态

Accepted（2026-09-22；决策来源 `架构/交付/DEXPI接入方案_2026-09-22.md` §4 决策 A；尚无代码引用）

## Context / 背景

DEXPI 接入落地前必须先钉死「存档格式是否改为 DEXPI」。不定这一条，导出器与持久化层的边界会在实现中被反复推翻。

两条事实使这个问题必须正面回答，而不能靠"以后再说"：

1. **DEXPI 是交换格式，不是状态格式。** 官方明确其往返有损，图形层"故意有损"——它的设计目标是让别的工具"读懂数据"，不是让某个工具"存下自己的全部编辑状态"。
2. **本项目的存档要承担完整编辑状态**，而不是交付视图。存档里有一批 DEXPI 根本没有对应物的东西（见 Consequences 正向第 1 条）。

用户提出这个问题的动机值得肯定：**双格式会漂移**。但"把原生格式换成 DEXPI"是消除漂移的一种解法，不是唯一解法；本 ADR 采纳的是更小代价的那一种（Decision 第 3 条）。

## Decision / 决策

1. **原生存档格式不变**：单个 `*.pid.json`，schema v3 及以后，自包含（用户图元包经 `gpEmbedUserPacks()` 内嵌），写入走 `GPAtomicFile` 原子写。
2. **DEXPI XML 定位为交换方言**：只作导出目标与导入来源，不参与原生持久化。导入侧产出 **v3 容器字典**后交给既有 `GPProjectImport` 管线，导出侧产出 XML 文本后由调用方落盘。
3. **消除第二套序列化的漂移风险**（这是对触发问题的正面回答）：DEXPI 适配器**只在 `GPPIDGraph.gpToDict()` 产出的 dict 上做变换**，不得从对象图另写一套序列化。沿用既有架构决策「core 对持久化只暴露 `gpToDict()` / `gpFromDict()`，新增持久化需求一律在 dict 上变换」——**单一事实源因此仍然只有一份**，转换层是纯函数，不是第二份真相。
4. **语义对齐、格式独立**：原生模型的**字段语义**向 DEXPI / ISO 15926-4 RDL 靠拢（首例即 `GPSymbolDef.gpComponentClass`［planned — v0.1 之后计划落地的字段，当前 `GPSymbolDef` 尚未含此属性；本 ADR 记录其决策，非现状］），但**容器格式与 schema 版本由本项目自控**。
5. **版本各自独立演进**：`GP_FORMAT_VERSION`（本项目）与 DEXPI 应用版本 / Proteus schema 版本互不绑定，二者通过映射表建立对应关系。

## Options considered / 备选方案

| 方案 | 判定 | 理由 |
|---|---|---|
| **A. 存档直接改为 DEXPI XML** | **否决** | 见 Consequences 的正负两侧；核心问题是格式性质错配与外部 schema 成为天花板 |
| **B. 存档保持 JSON + DEXPI 作交换格式** | **采纳** | 单一事实源不变、外部标准不构成约束、可并行支持多个标准 |
| **C. 双格式并存（同时写 `.json` 与 `.xml`）** | 否决 | 两倍存储、两份必然不同步、原子写与失败回滚复杂度翻倍；且违反"只留一份真相" |

## Consequences / 后果

### 正向

- **存档能承载 DEXPI 无对应物的完整编辑态**：`drop_restore`（落点恢复注册表）、`gpSchemaFingerprints`（库指纹快照）、`gpShapes`（自由注释层）、`gpEdge.gpRouting`（正交布线拐点）、`gpLabelAnchor` / `gpLabelOffset`（归一化标签位置）、`tag_seq`（位号水位线）、`gpTagRules`（项目编号规则），以及将来的视口状态。这些若塞进 DEXPI 的扩展命名空间，得到的是「DEXPI 皮的私有格式」——**标准的合规性会变成假象**。
- **外部 schema 不构成天花板**：DEXPI 2.0 定稿或发生破坏性变更时，只影响映射表与适配器，**不触发存档迁移**。反之若存档即 DEXPI，标准一换代，全部既有存档都要迁移，而迁移代码仍得自己写。
- **可并行支持第二个标准**（CFIHOS / ISA / 客户私有交付模板）。这是 Y3 判据「规则覆盖第二个标准体系」的前提——存档与某一个标准绑定后，这个能力就没了。
- **与品牌承诺一致**：存档是「画得出来」（完整编辑态），DEXPI 是「交得出去」（交付视图）——与「开源的是画得出来，付费的是交得出去」这条边界同构。一个格式承担两种职责，两种都会做不好。
- **既有持久化链路与断言不重写**：`JSON` 解析、`GPAtomicFile` 原子写、`GPSchemaMigrate` 幂等迁移链（仅读取路径）、`GPImportReport` 校验，以及围绕它们的 GPGTest 套件全部保留。

### 负向

- **必须维护一份映射表**（类 / 属性 / 单位 / 信号），并承担其与代码漂移的风险。
  → 缓解：映射表以数据文件落地（`res://data/dexpi/`）+ 专门测试套件断言覆盖；由于 Decision 第 3 条，漂移面被**限制在数据层**，不会蔓延到序列化逻辑。
- **导出是一次有损投影**，用户需理解"存档 ≠ 交付物"。
  → 缓解：导出经 `GPImportReport` 逐条列出丢失项（悬空端、未声明类、注释图形等），不静默。
- **Godot 无 XML 写器**，XML 文本构造需自研（转义、UTF-8 声明、半角小数点）。
  → 已记录于 `DEXPI接入方案_2026-09-22.md` §6 陷阱 2。

### ⚠️ 必须先写清、避免未来误读的负向

- **若把 DEXPI 作为原生格式，会造成「虚假的可移植性」。** 客户看到 `.dexpi.xml` 会以为"任何 DEXPI 工具都能完整打开"，实则本项目的私有编辑态全部躺在扩展命名空间里，**别的工具读入即丢失**。
  这比现状**更糟**：现状明确区分「原生存档」与「交付视图」，边界清晰且诚实；换成 DEXPI 原生则把这个边界藏起来了，而藏起来的那部分恰好是用户最可能依赖的。

## 可迁移的判断准则

当遇到「能否用一个外部标准格式替代自有格式」这类问题时，先问一句：

> **该格式的设计目的是「交换」还是「承载状态」？**

交换格式的优化目标是互操作与语义可读，必然对私有状态有损；状态格式的优化目标是完整还原，必然包含外部读不懂的东西。**两者不可兼得，用一个去替代另一个，损失一定出现在你没注意到的那一侧。

## 许可与商标合规（2026-09-23 追加）

> 触发问题：DEXPI 是否可免费引用并集成进 G-PID 商业销售？
> 结论：**可以**——DEXPI 是免费、开放、可商业使用的标准，但需满足署名义务、并回避一个版本许可陷阱。

- **许可事实**：DEXPI **2.0.0** 规范与 XSD 以 **CC BY 4.0** 发布（DEXPI Initiative；dexpi.gitlab.io 规范页与 Equinor/neqsim 文档均确认 "official DEXPI XML V2.0.0 XSD is bundled under CC BY 4.0"）。
  CC BY 4.0 授予：商业使用、修改、再分发、**闭源集成（无 copyleft、不传染）**——这正是本项目 Open-Core（Core MIT + Pro 私有）能合法成立的法律基础。
- **署名义务（必须）**：在软件第三方许可声明（THIRD_PARTY_LICENSES）中列出 DEXPI、链接 CC BY 4.0、注明所用版本（如 2.0.0）、保留 XSD 文件内版权头；**不得暗示 DEXPI Initiative 背书或认证本产品**。
- **⚠️ 版本陷阱**：DEXPI 1.x（含 1.0 PDF 规范）早期以 **CC BY-SA 3.0** 发布（share-alike，具 copyleft）。**本项目针对 2.0.0（CC BY 4.0）实现**，既避开 BY-SA 纠缠，也卡准 ADR-8 原定的 2.0 换代窗口。官方 XSD 仓库已从 GitHub 迁至 GitLab（github.com/DEXPI/Specification 已废弃，redirect 至 gitlab.com/dexpi/Specification）。
- **商标边界**："DEXPI" 为 DEXPI Initiative 商标。允许描述性使用（如"G-PID 支持 DEXPI 2.0 导入/导出"）；**不得自称"DEXPI 认证 / 官方推荐"**，除非正式通过其后端 conformance 程序（当前 governance 未公开、不建议宣称）。
- **RDL / ISO 15926**：引用 RDL 类名作枚举值（事实性标准用语）不受版权限制；若捆绑整个 RDL 数据库再分发，需另行确认 dexpi.org 上的许可——保守做法：仅引用类 ID，不打包整库。
- **专利**：CC BY 4.0 仅覆盖版权，不授予专利许可；但作为标准消费者（产出 / 消费 XML）专利风险极低，可忽略。
