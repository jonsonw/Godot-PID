# ADR-4：存档原子写

> 本 ADR 规定「写入工程文件」必须走「临时文件 → 校验 → 备份 → 重命名覆盖」，绝不直接改写目标文件。

## Status / 状态

Accepted（代码引用见 `io/atomic_file.gd:23`、`io/project_io.gd:34`）

## Context / 背景

工程存档是用户的交付物，一旦在保存过程中崩溃或断电，留下半截文件（JSON 截断 / 校验和不符）就是灾难性数据丢失。朴素写法是 `FileAccess.open(path, WRITE)` 直接覆盖——中途失败必然产生损坏文件。`GPAtomicFile` 正是为消除这一风险而建。

需要一条「要么完整落盘、要么原文件不动」的写入契约。

## Decision / 决策

1. **先写临时文件**：序列化文本写入 `path + ".tmp"`（同目录，保证同文件系统可 rename）；
2. **校验**：临时文件写完即重新打开读取，校验字节数与（可选）JSON 合法性；校验失败则删除临时文件并保留原文件，向上报错；
3. **保留备份**：`path` 已存在时先 rename 为 `path + ".bak"`（仅保留最近一份），再让临时文件 rename 为 `path`；
4. **失败回滚**：任何一步异常都回退到「原文件不动」状态，不泄漏半成品；
5. **统一入口**：所有工程文件、图元包、导出包的写入都经此路径，不允许业务代码直接 `FileAccess` 写目标路径。

## Consequences / 后果

- 正向：保存过程崩溃不会损坏既有存档；`*.bak` 提供一次人工兜底恢复机会；写路径只有一处，易于审计与加固。
- 负向：每次保存多一次「临时文件 + 校验 + 备份」开销，超大工程保存略慢（工程规模下可忽略）；
- 负向：需保证临时文件与目标同处一个磁盘分区，否则 rename 退化为拷贝、原子性失效——实现须显式校验同目录。
