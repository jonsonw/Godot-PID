# ADR-2：存档容器 —— 单一格式，三种 kind

> 本 ADR 把「P&ID 工程的多种产物如何序列化」钉定为：一种 JSON 容器、由 `kind` 字段区分，而非三种扩展名。

## Status / 状态

Accepted（代码引用见 `io/schema_migrate.gd:44`、`io/project_export.gd:4`、`io/project_import.gd`）

## Context / 背景

项目需要持久化多类产物：工程文档（`*.pid.json`）、图元包（用户自定义符号）、导出包（交付 / 互操作）。朴素做法是给每类产物一个扩展名（`*.proj` / `*.pack` / `*.exp`），各有各的加载器与迁移链。但这会带来三套几乎重复的 IO 代码、三套迁移链、三套原子写实现，且将来新增产物类型（如多文档、3D 联动）又要再开一条线。

需要一套统一约定，使「序列化」这件事只有一条路径。

## Decision / 决策

1. **单一容器格式**：所有产物共用同一个 JSON 容器 schema（以 `.pid.json` 为唯一扩展名）；
2. **`kind` 字段区分**：容器顶层 `kind` 取值区分用途，当前三种：`"project"`（工程文档）/ `"symbol_pack"`（图元包）/ `"export"`（导出包）；
3. **同一套管道**：三类产物都走同一条原子写路径（ADR-4）与同一条版本迁移链（v1→v2→v3）；迁移链在 dict 上做变换且幂等，不区分 kind 各自实现；
4. **加载时按 `kind` 分派**：读入后由各自的 `GPProjectIO` / `GPSymbolPack` / `GPProjectExport` 接管，但「读文件」这一动作只做一次。

## Consequences / 后果

- 正向：IO 代码量大幅下降；新增产物类型只需新增一个 `kind` 值与一处分派，不必再开一条序列化链路；存档层（src/save）与导出层共享同一套写入/迁移原语。
- 负向：读取方必须按 `kind` 分派，类型安全弱于「三种独立类」；`kind` 取值需纳入迁移链的保护（未知 kind 视为解析失败而非静默忽略）。
- 负向：单一大容器使文件体量随工程增长而增大，需配合 ADR-4 的原子写与 ADR-6 的导入非破坏策略才能安全地做增量处理。
