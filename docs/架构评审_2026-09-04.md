# Godot-PID 代码架构评审报告

- **评审日期**：2026-09-04
- **评审范围**：`src/ui/*.gd`、`src/core/*.gd`（约 5925 行）
- **评审方式**：静态代码审查；**仅评估与给出重构方案，不改动任何代码**
- **目标**：检查重复/相似逻辑、职责过大的函数与模块、过度耦合、适合抽象为类的部分

---

## 一、总体评价

项目分层方向正确：**`core`（模型）/ `ui`（视图）/ `graph_binder`（视图↔模型绑定）** 三层清晰。下列是已经做对、应作为后续重构范本的部分：

- **`GPShape`（shape.gd，129 行）**：强类型几何图元，自带 `gpToDict()` / `gpFromDict()` / `gpBBox()`，数据主权与序列化边界清晰，是很好的模型范本。
- **`GPPIDGraph`（pid_graph.gd，223 行）**：强类型集合容器，`gpAddShape()` 等接口稳定。
- **`GPGraphBinder`（graph_binder.gd，164 行）**：视图投影 + 增量同步，把"模型变更"与"Node2D 节点树"解耦得干净，是视图层的最佳实践。
- **信号事件流**：`canvas_2d.gd` 已建立 `gpGraphChanged` / `gpStatusUpdated` / `gpMakeSymbolRequested` / `gpSymbolEditRequested` 等信号，解耦雏形已成。

核心痛点（按严重程度排序）：

1. **主画布与符号编辑画布近平行实现** —— 抓取点、命中测试、框选、右键菜单各写两遍。
2. **同一"几何图元"存在三套数据表示** —— `GPShape` / 原始字典数组 / `GPSymbolDef.gpPorts`，转换散落多处。
3. **`main_window.gd`（997 行）偏胖** —— 合成根同时揽工程 IO（读写存档）。
4. **单个画布文件超大**（1463 / 1215 行）混合相机、绘制、选择、抓取点、菜单、连接预览等关注点。

## 二、重复 / 相似代码逻辑（最严重问题）

### 2.1 抓取点（Grip）编辑逻辑双份实现

| 项 | 主画布 `canvas_2d.gd` | 符号编辑 `glyph_canvas.gd` |
|---|---|---|
| 角色常量 | L67–71（`GP_GRIP_ENDPOINT/CENTER/RADIUS/CORNER/VERTEX`） | L84–92（同名常量） |
| 抓取点生成 | `_gpRectCorners` L943、`_gpShapeGrips` L956 | `_gpRectCorners` L850、`_gpShapeGrips` L757 |
| 命中测试 | `_gpHitGrip` L979 | `_gpHitGrip` L781 |
| 开始拖动 | `_gpStartGripDrag` L994 | `_gpStartGripDrag` L796 |
| 拖动重算 | `_gpOnGripMove` L1001 | `_gpOnGripMove` L811 |

**当前问题**：同一套"几何图元 → 抓取点列表 → 命中 → 拖动时几何变更（端点平移 / 圆心+半径 / 固定对角角点缩放 / 顶点）"逻辑在两文件各实现一遍，唯一差异是底层数据结构不同（`GPShape` vs 原始字典）。两处必须同步维护，已出现漂移隐患（矩形角点缩放的重算公式各写一份，行为细节易不一致）。

**建议抽离**：`GPShapeGripEditor`（置于 `core/` 的纯几何工具类，或 `ui/` 下的可复用 Component）

- **职责**：输入统一图元几何，输出三类纯几何能力，完全不依赖 `Control` / `Node2D`：
  - `gpGrips(gpShape) -> Array[Dictionary]`：按图元类型返回 role/pos 列表
  - `gpHitGrip(gpWorld, gpGrips) -> Dictionary`：返回被命中的抓取点
  - `gpApplyGrip(gpShape, gpGrip, gpWorld) -> void`：按 role 统一重算（端点/圆心+半径/固定对角角点/顶点）
- **收益**：主画布与符号编辑的抓取点行为 100% 一致；新增图元类型（椭圆、圆弧）只改一处；逻辑可在 headless 下单测。

### 2.2 几何命中 / 包围盒工具重复

| 函数 | `glyph_canvas.gd` | `canvas_2d.gd` |
|---|---|---|
| 点到线段距离 | `_gpDistPointSeg` L865 | `_gpDistPointSeg` L920 |
| 单图元包围盒 | `_gpPrimBBox` L878 | （内联于 `_gpHitShapePrim`） |
| 命中测试 | `_gpHitPrim` L927、`gpPick` L952 | `_gpHitShape` L887、`_gpHitShapePrim` L899 |
| 数组包围盒 | `_gpArrBBox` L904 | — |

**当前问题**：基础几何（点到线段、AABB、命中）在两处各写；`GPShape.gpBBox()` 已存在但符号编辑器未复用，仍自己维护字典包围盒。

**建议抽离**：`GPGeometry`（`core/` 静态工具类）

- `gpDistPointSeg`、`gpPointInRect`、`gpRectCorners`、`gpHitTest(gpShape, gpWorld, gpTol)`
- 统一服务两个画布的命中、框选、状态栏坐标显示。
- **收益**：core 纯函数可单测；UI 不再各自维护几何；`GPShape.gpBBox` 成为唯一包围盒来源。

### 2.3 框选 / 选择集管理重复

| 函数 | `canvas_2d.gd` | `glyph_canvas.gd` |
|---|---|---|
| 提交框选 | `_gpCommitMarquee` L1121 | `_gpCommitMarquee` L562 |
| 选择集 | `_gpSetSelection` L1160 | `_gpSelectAll` L621、`_gpPruneSelection` L615、`_gpIsSelected` L736 |
| 框选几何 | — | `_gpMarqueeMode` L970、`_gpPrimInMarquee` L976、`_gpMarqueeSelect` L984、`_gpPruneStatic` L995 |
| 选择高亮 | `_gpDrawShapes`（部分） | `_gpSelectionBBox` L745 |

**当前问题**：选择集（单/多）、框选矩形求交模式（包含/相交）、删除、全选、ESC 回退逻辑重复；符号编辑器还额外维护 `prune` 逻辑应对增删后的索引失效。

**建议抽离**：`GPSelectionModel`（RefCounted，持有统一 SelectedSet 引用）+ `GPSelectTool`（框选几何策略）

- 主画布选"图元 + 注释图形"，符号编辑选"图元原语"，可由同一选择模型 + 不同命中器注入。
- **收益**：选择 / 删除 / 全选 / ESC 行为统一；索引失效由模型层统一处理；便于挂接 undo/redo。

### 2.4 右键上下文菜单构建重复

| 项 | `canvas_2d.gd` | `glyph_canvas.gd` |
|---|---|---|
| 菜单构建 | `_gpShowContextMenu`（约 L1100+） | `_gpShowContextMenu` L670 |
| id 分发 | `_gpOnContext`（含"创建图元/修改图元"） | `_gpOnContext` L713 |
| 菜单项常量 | `GP_CTX_*` 一组 | `GP_CTX_*` 一组 |

**当前问题**：菜单项定义 + id 分发各写一遍，`GP_CTX_*` 常量两组独立编号，易 id 漂移。

**建议抽离**：`GPContextMenuBuilder`（或"菜单项声明表"）

- 画布只声明"当前上下文可用项"（枚举 + 标签 + 可见性谓词），通用渲染器负责 `popup` 定位与 `id_pressed` 回调。
- **收益**：菜单项与 id 集中维护，跨画布一致；新增菜单项不碰分发分支。

## 三、数据模型三套格式不一致（耦合根因）

**现状** —— 同一"几何图元"有三种表示：

1. 主画布注释图形：`GPShape`（强类型，shape.gd）
2. 符号编辑器图元：`gpPaths` / `gpCircles` / `gpRects` / `gpPorts` **原始字典数组**（glyph_canvas.gd：L221 `gpLoadShapes`、L337 `gpGetDraftShapes`）
3. 符号定义端口：`GPSymbolDef.gpPorts`（symbol_def.gd，第三套字典结构）

**接缝胶水**（转换散落多处）：

- `canvas_2d.gd` L1048 `_gpShapesToDraft`：把 `GPShape` → 符号编辑器字典格式
- `graph_binder`：把 `GPShape` → `GPSymbolView` 节点

**当前问题**：新增图元类型（如椭圆、圆弧）需在 3+ 处同步修改；数据主权统一受挫；抓取点/命中/渲染因此无法复用（正因 2.1/2.2 双份实现）。

**建议：统一为 `GPShape` 单一图元模型**

- 符号编辑器内部也改用 `Array[GPShape]`（及 `GPPort` 列表），删除字典数组。
- `GPSymbolDef` 持有 `Array[GPShape]` + `Array[GPPort]`，删除 dict 端口。
- `GPShape.gpToDict()` / `gpFromDict()` 仅作存档边界；UI 内部全用强类型。
- **收益**：抓取点 / 命中 / 渲染全部复用同一套；删除 `_gpShapesToDraft` 接缝胶水；新增图元一处改。

## 四、职责过大的函数 / 模块

### 4.1 `main_window.gd`（997 行）偏胖

**当前职责混合**：合成根 + 工程 IO + 菜单栏装配 + 工具栏装配 + 画布/隔离层装配 + 事件路由。

工程 IO 相关：`_gpWriteProject` L492、`_gpReadProject` L514、`_gpSaveProject` L462、`_gpOpenProject` L475、符号包导出 `_gpOnPackExported` L784。

**建议拆出**：`GPProjectIO`（RefCounted）

- **职责**：加载 / 保存 / 新建 `*.pid.json`，序列化版本与迁移，符号包导出。
- `main_window` 只做装配与路由，调用 `GPProjectIO`。
- **收益**：IO 可在 headless 下单测；存档格式演进独立；`main_window` 瘦身到 ~600 行。

### 4.2 单画布文件超大（1463 / 1215 行）

`canvas_2d.gd` 内混合：相机（L311–334）、工具绘制（L749–807）、选择（L573–690）、抓取点（L943–1055）、注释图形 CRUD、菜单、连接预览（L386）。
`glyph_canvas.gd` 内混合：工具分派（巨型 `match gpTool`）、相机/guide/scale、选择、抓取点、端口、撤销（`gpUndo` L292）。

**建议拆出**：

- **`GPCanvasCamera`**（Component/RefCounted）：平移 / 缩放 / 屏幕↔世界变换（L311–334、L320–326）。两画布共用（符号编辑用 author-space 固定缩放，可参数化启用/禁用 zoom）。
- **`GPAnnotationLayer`**：注释图形 CRUD。已部分在 `gpShapes`，抽为独立 Node/资源，主画布组合它（符号编辑器不需要）。
- 输入处理见 4.3 的 Tool 策略模式。
- **收益**：单文件可维护；各部件可独立测试。

### 4.3 `glyph_canvas.gd` 巨型 `match gpTool` 分派

**位置**：`_gui_input` 内 `match gpTool`（约 L378–530），每个工具分支内联绘制/提交逻辑。

**建议：Tool 策略模式**（`GPITool` 接口 + `GPSelectTool` / `GPDrawLineTool` / `GPDrawCircleTool` / `GPDrawRectTool` / `GPPolylineTool` / `GPPortTool`）

- 画布持有 `gpCurrentTool`，转发 `gui_input`；新增工具不碰画布主逻辑。
- **收益**：绘制工具可独立测试与扩展；消除巨型 `match`；与 2.1/2.3 的复用自然衔接。

## 五、过度耦合

### 5.1 画布直接计算窗口坐标做菜单定位

- `canvas_2d.gd`：右键菜单定位用 `get_window().position`（本轮已修正过一次偏移）。
- `glyph_canvas.gd` / `symbol_isolation_layer.gd`：右键 / 下拉定位同样自己算屏幕坐标。

**当前问题**：屏幕坐标换算逻辑散落三处，本轮就因换算公式错误返工一次。

**建议**：收口到一处 `GPPopupHelper.popup_at_cursor(popup, offset)` 静态工具，封装正确的屏幕坐标换算；画布只调用，不自己算窗口坐标。

- **收益**：定位逻辑单一来源，避免再次漂移。

### 5.2 符号编辑器与 `GPCenterArea` / `GPSymbolIsolationLayer` 强耦合

**现状**：`main_window` 直接 `add_child` 隔离层、connect `gpSaved`（L583 / L729 / L761），隔离层持有 `GPGlyphCanvas`。

**建议**：隔离层作为独立模态编辑器，通过 `Resource`（`GPSymbolDef` 草稿）与外界通信，关闭时回传；`main_window` 只做"打开 / 接收结果"。

- **收益**：符号编辑可独立实例化与单测；合成根职责收敛。

## 七、重构优先级与路线图

- **P0 — 统一图元模型 `GPShape`**：解锁 2.1/2.2/2.3 的全部复用，是其余重构的前提。
- **P1 — 抽离 `GPGeometry` + `GPShapeGripEditor` + `GPCanvasCamera`**：消除主画布 ↔ 符号编辑的双份实现。
- **P2 — `GPSelectionModel` + Tool 策略模式 + `GPContextMenuBuilder`**：选择/工具/菜单三件套统一。
- **P3 — `GPProjectIO` 拆离 `main_window`**：IO 单测与格式演进独立。

> 建议按 P0→P1→P2→P3 顺序，每步保持 headless 编译零错误、并保留 `GPShape.gpToDict/gpFromDict` 存档兼容。

## 八、重构后收益

- **新增图元类型**：从 3+ 处改动 → 1 处（`GPShape` 子类 + `GPShapeGripEditor` 一处）。
- **行为一致性**：抓取点、菜单、相机各一处实现，主画布与符号编辑表现统一。
- **可测试性**：`core` 纯几何（`GPGeometry` / `GPShapeGripEditor`）可 headless 单测；画布经信号解耦可实例化测试。
- **可维护性**：单文件目标 < 600 行；变更成本显著下降；消除"改一处忘改另一处"的漂移类缺陷。
